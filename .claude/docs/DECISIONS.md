## v0.1.4 decisions (team blockers on v0.1.3, 2026-08-17)
- **SA-020 Sub-agent allowlist IS platform-enforced — correcting SA-015.** The v0.1.3 statement "Claude Code has no hard sub-agent allowlist" was **wrong**. Claude Code supports `tools: Agent(name1, name2, ...)`, which restricts which sub-agents an agent may spawn (docs: code.claude.com/docs/en/sub-agents#restrict-which-subagents-can-be-spawned). The orchestrator now declares `Agent(pm, architect, designer, shopify-developer, qa, code-review, delivery-head)`; a bare `Agent` or any name outside the seven is rejected by both the platform (when the orchestrator runs as main agent) and by `validate-plugin.py`/acceptance T4. Verified: the string-form `tools:` line passes `claude plugin validate --strict`.
- **SA-021 QA is tool-level read-only; execution is delegated.** QA holds `[Read, Grep, Glob]` and does **not** run tests itself. CI (`.github/workflows/app-ci.yml`) or an authorized human/executor runs the suite and writes immutable artifacts (JUnit/coverage/logs, webhook/billing probe outputs); QA reads those artifacts, judges G4/G5 against acceptance criteria, and returns a verdict to the orchestrator, which records it. The implementation agent's own claim that its tests passed is never the sole evidence.
- **SA-022 Pre-launch performance wording de-drifted.** Milestone QA (G5) is "milestone regression, architecture fitness, and applicable baseline performance." Production Core Web Vitals (LCP/CLS/INP) are measured **post-launch** for Built-for-Shopify eligibility only — never a pre-submission store-listing gate.
- **SA-023 Activation corrected.** `settings.json` uses the plugin-local `{"agent": "orchestrator"}`. `claude plugin details <name>` requires the plugin to be **installed** (e.g. via a local marketplace); it does not accept `--plugin-dir`. _(The main-agent vs subagent enforcement distinction is refined in SA-025.)_
- **SA-024 CLI component inventory is verified, not assumed.** Acceptance installs the plugin and asserts `claude plugin details` reports exactly 8 agents + 11 skills with no `_`/probe scratch components — catching stray files the frontmatter-only parse would miss. _(Made isolated + unfiltered in SA-026/SA-027.)_

## v0.1.5 decisions (team blockers on v0.1.4, 2026-08-18)
- **SA-025 Allowlist is enforced ONLY for the main agent — refines SA-020/SA-023.** Per code.claude.com/docs/en/sub-agents#restrict-which-subagents-can-be-spawned: *"The `Agent(agent_type)` allowlist syntax applies only to an agent running as the main thread with `claude --agent`. In a subagent definition … any type list inside the parentheses is ignored."* So the seven-specialist restriction is platform-enforced when the orchestrator is the **main** agent (settings default or `--agent`), but **not** when it is invoked as a subagent via `@`-mention/typeahead — there the rule rests on the orchestrator's instructions. Docs (`orchestrator.md`, `README.md`, `INSTALL.md`, `cold-plugin-discovery.md`) state this explicitly and no longer list `@agent-…` as a main-agent path. The cold-session rejected-agent test is run **only** after confirming main-agent mode.
- **SA-026 T10 runs under an isolated `CLAUDE_CONFIG_DIR`.** Every marketplace/install/details/uninstall/remove command in T10 goes through `CLAUDE_CONFIG_DIR="$WORK/claude-config"` (ref: code.claude.com/docs/en/env-vars — it overrides the config dir where settings, session history, and plugins live). The operator's real `~/.claude` is never modified; teardown uses the qualified `webdesk-shopify-apps@wsa-accept --scope local`, never an unqualified uninstall against the normal environment.
- **SA-027 T10 tests the EXACT shipped package, unfiltered.** The prior `tar --exclude`/`rm` pre-clean masked the very packaging defect T10 claims to detect. T10 now `cp -a "$ROOT/."` and installs it as-is; any unexpected component (`_*`/`probe*`, or a count ≠ 8 agents/11 skills) **fails** the test. The `_probe`/`probe-bad` scratch components were deleted from the source tree so the real package is clean.
- **SA-028 Pilot install scope is project-bounded.** Because the plugin ships a default `agent`, a user-scope install makes the orchestrator active in every enabled project. Pilot docs install from inside the Rossy repo with `--scope local` (or `--scope project` to share via `.claude/settings.json`), and the default user scope is only recommended with an explicit caveat.
- **SA-029 Read-only agents have an EXACT tool set.** `qa` and `code-review` must declare exactly `[Read, Grep, Glob]`; `validate-plugin.py` and acceptance T5 reject Bash, Agent, Write, Edit, or any other tool (previously only Write/Edit were rejected, leaving Bash/Agent as a hole).
- **SA-030 QA evidence needs provenance, and QA proposes (not writes) the audit log.** Every QA evidence set must carry commit SHA, CI run ID / executor identity, execution timestamp, test environment, artifact source, and the store/build identifier; QA marks evidence **BLOCKED** if provenance is missing or the artifact does not match the commit under review. QA has no write tools, so it **returns the proposed `audit_log` entry to the orchestrator** rather than "logging" it.
- **SA-031 Cold-session skill-preload uses per-skill canaries.** Preload is proven by asking each agent a question whose answer is a token unique to a specific skill body (absent from the agent body), for **every** declared skill across all eight agents — a fact duplicated in the agent body (e.g. bad-HMAC = 401) is not preload proof. Remains NOT EXECUTED (interactive).
- **SA-032 Release evidence ships in the package.** `RELEASE-EVIDENCE.md` contains the full unedited negative-test + acceptance output (bare Agent; missing/extra specialist; QA+Bash; invalid skill preload; `2026-02` and `2026-13`; wrong default-agent; exact unfiltered inventory; T10 under isolated `CLAUDE_CONFIG_DIR`; `PASSED=10 FAILED=0 SKIPPED=2`). The two external tests remain NOT EXECUTED and are not fabricated. _(Superseded on count by SA-035: T11 makes it PASSED=11.)_

## v0.1.6 decisions (team blockers on v0.1.5, 2026-08-18)
_No Shopify application rules or delivery workflow changed in v0.1.6._
- **SA-033 Preload proof uses opaque tokens, not semantic canaries — replaces SA-031.** A semantic canary can be answered from the agent body or general knowledge, so it never proved *preload*. Each skill now carries exactly one high-entropy `WSA-PRELOAD-<skill>-<16-hex>` token, present once in its `SKILL.md` and nowhere else in the package. Only an agent whose context received that skill body can reproduce the meaningless token.
- **SA-034 Token values are opaque and never printed.** They do not appear in `cold-plugin-discovery.md`, agent bodies, other docs, or `RELEASE-EVIDENCE.md`; validators report them masked and discover them by pattern (no hard-coded values). The cold plan asks each agent for its per-skill token and the reviewer compares against the `SKILL.md` marker.
- **SA-035 Cold-test preload passes only with zero lookup.** A row passes iff the agent returns the exact token **and** no `Read`/`Grep`/`Glob`/`Bash`/`Skill`/file-discovery call occurs in that turn **and** the transcript/debug trace confirms no lookup. A lookup proves discoverability, not preload → the row fails. Enforced structurally by `validate-plugin.py` + acceptance **T11** (one token per skill, unique, no leak); the zero-lookup behavioural check is part of the NOT-EXECUTED interactive cold plan.
- **SA-036 Evidence isolation proof corrected.** `RELEASE-EVIDENCE.md` no longer shows a marketplace id inconsistent with T10, and drops the claim that equal before/after `plugin list` line counts prove the real config was untouched (a negative that count can't establish). Isolation now rests on the documented `CLAUDE_CONFIG_DIR` override + a disposable working dir + explicit runtime assertions printing both the isolated config path and positive proof the install record landed inside the throwaway config.

## v0.1.7 decisions (team blocker on v0.1.6, 2026-08-18)
_No Shopify application rules, agents, permissions, delivery gates, or workflow content changed._
- **SA-037 Preload marker is visible and self-authorizing — corrects SA-034 wording.** The v0.1.6 marker was an HTML comment saying "do not remove, copy, or print elsewhere." Since the full skill body is preloaded, a correctly-preloaded agent could obey that and refuse to return its token, producing a false cold-test failure. The marker is now a **visible** Markdown line that explicitly authorizes returning the exact token, without any tool, when asked during the documented cold test. The "do not print/return" wording is removed; leak-prevention stays enforced by the validator, not by instructing the agent. Token values are unchanged and still never printed in docs/evidence.
- **SA-038 Validator/T11 enforce visibility + skill-name match.** In addition to the SA-033/SA-035 checks, `validate-plugin.py` and T11 require: exactly one token that **survives HTML-comment stripping** (proving it is a visible marker, not hidden in a comment), and a token whose embedded skill segment **equals the owning skill directory** (`WSA-PRELOAD-<dir>-<16 hex>`).
- **SA-039 Cold test: one fresh invocation per (agent, skill) pair.** Each pair is asked in a brand-new agent invocation with no resumed/reused conversation and exactly one question, so a prior turn's lookup cannot leave a token in context and yield a false PASS. The zero-tool-call / transcript-confirms-no-lookup pass rule is retained.
